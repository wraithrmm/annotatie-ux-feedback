Viewport

Phone layout, 390 px — designed first

The frames below are drawings of the phone layout at 390 px, made before the tablet and desktop layout. On a phone the Report control lives in the 56 px app bar, before Help, so it can never cover a bottom bar, a primary action or the navigation; report mode adds a bar under the app bar that pushes the page down rather than covering it; the comment panel is a bottom sheet (MOB-r1 §3.11) that fills the screen once the keyboard opens; threads and lists are full-height sheets (§3.13). The live frame further down is where every state is operated.

Live frame — every state, at 390, 820 and 1280 px

Press Report to enter report mode; point at or tab to any part of the page and press it (or Enter) to report on it; press a pin to open its thread; press Reports in the mode bar for this page's list and My reports. Esc closes the open panel, then leaves report mode. The state switch above jumps to any state, including the server outcomes a click cannot produce.

Review notes: 14 assumptions and open questions
  • RW-A1 — where the Report control sits. At 1024 px and up it floats at the bottom-end corner, 24 px in, and lifts by the height of any sticky bottom bar or toast stack the page shows (measured from the page's data-bottom-bar elements), so it never covers a bulk bar or a toast. Below 1024 px it is a button in the 56 px app bar, before Help: a floating button on a phone would cover the one bottom bar M-11 allows. It is therefore "a corner" at both sizes (bottom-end on a desktop, top-end on a phone and tablet), not one corner. Concerns: the Report control in every state.
  • RW-A2 — the count on the Report control. The neutral pill counts this page's reports that are not yet resolved (Open, Answered, In progress), including one whose part has gone. It is never magenta: the reports are everyone's, not the signed-in person's own queue (rule 26). Nothing at 0. Concerns: the Report control and the Reports button in the mode bar.
  • RW-A3 — the status tone map for reports. Open: neutral, minus-circle. Answered: info, chat bubble. In progress: neutral, clock. Resolved: success, the open check, and a dashed pin. Open and In progress share a tone and are told apart by icon and word. Concerns: every status tag and pin.
  • RW-A4 — report numbers. Reports are numbered in one sequence across the system ("Report 41") so a pin, a list row and a thread name the same thing on every page. design.md's table has no number column; a number derived from creation order is assumed (question Q1 in the report). Concerns: pins, list rows, thread headings.
  • RW-A5 — Bug is chosen when the comment panel opens. design.md says nothing but the comment is required, so the type starts on Bug and can be changed. Concerns: the Type control.
  • RW-A6 — the comment's length limit. 5,000 characters, refused by the server with "Your comment is 5,213 characters. Shorten it to 5,000 or fewer." (ST-2); not drawn as a counter. The figure is assumed (question Q2). Concerns: the Comment and Your reply fields.
  • RW-A7 — a reply from the reporter re-opens an answered report. Answered means "a reply waits for the reporter"; once the reporter replies the report goes back to Open. A reply from anyone else leaves the status unchanged. Concerns: the thread's reply and status sentence.
  • RW-A8 — after Send, report mode stays on. The person can report a second thing straight away; Close on the sent panel returns them to report mode, Done leaves it. Concerns: the sent state.
  • RW-A9 — "Sign in again" opens the app's sign-in in a new tab so the comment kept in this tab survives; the prototype's link goes to example.org. Concerns: the signed-out state.
  • RW-A10 — a person with the read permission only sees pins and threads, and a Report control labelled "Reports" that opens the list rather than report mode; no reply box, no Resolve or Reopen. Concerns: the read-only state.
  • RW-A11 — My reports on another page. In the app a row for another page opens that page at the pin with the thread open. The prototype draws only the register, so those rows open the thread here, with "Go to Today" as a link. Concerns: My reports rows for Today and Status view.
  • RW-A12 — the host page is abridged. The register is S-306's list cut to six rows with no filters, and the menu is S-101's without the Rules and configuration and Performance reviews groups. Outside report mode the host's own controls (menu items, Help, Export this list, row links) go nowhere in this file; only the widget and the navigation drawer are live. Concerns: the host page, not the widget.
  • RW-A13 — the replier's name. Replies show as the product owner's account, as D-499 (3) requires; it is the one real name in the file and appears only as a reply author. Concerns: threads 41, 44, 29 and 36.
  • RW-A14 — the copy of the page is raw (D-499 (5)). The comment panel says so in one sentence ("A copy of this page as you see it is sent with your report, with password fields left blank"), so nobody reports from a page showing something they would not send. Concerns: the note in the comment panel.

Where every part comes from

  • Behaviour — design.md §1–§6 (D-499): the Report button in a corner of every page; report mode's capture layer (nothing on the page runs); hover outline, click to place a pin, "Comment on the whole page", arrow keys / Tab and Enter; type Bug / Feature / Question; the snapshot refused above 2 MB with a page-level note; pins placed by selector, then readable anchor, then page-level; statuses Open, Answered, In progress, Resolved; "Show resolved pins"; My reports and the page's list; everyone permitted sees and answers every report.
  • Invisible without the permission — design.md §2: the directive renders nothing at all, so the "Without the permission" state is the S-101 page with no widget markup.
  • Frame — S-101 (the staff shell), its tokens, sidebar, app bar, banner and page-header anatomy copied unchanged; the staging banner because the tool runs on staging only (D-499 (2)).
  • Host list — S-306: list rows below 640 px (M-1, M-15), the captioned table from 640 px, the result line with positions and people labelled and never added (rule 14).
  • Panels — S-101's Help flyout (25rem, palette §4.7) at 640 px and up; MOB-r1 §3.13 full-height sheet below; S-415's sheet footer; MOB-r1 §3.11 bottom sheet for the comment panel; palette §4.2 error summary and the 4px error bar; §4.4 callouts (never a toast for an error, rule 8); §4.6 tab counts as neutral pills.
  • People — the synthetic register: Ellis Varnholt (signed in, staff administrator), Eero Halmelahti (FINX915), Lavanya Kodandaram (INDX942) as other testers; the officials in the host list from the register's cast. No new name was invented.
